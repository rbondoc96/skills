Engineering readout · Retry behavior

A retry should return the first result.

A timeout can hide a successful write. If the retry looks like a new operation, the server may save the same record twice.

● Duplicate writes observed Proposed fix · Stable request key
Reuse the request key across attempts.

In this fictional controlled test, duplicates fell from 8 in 100 requests to 0 in 100. The p95 latency increased by 15 ms. Concurrent retries and key expiry remain untested.

01

Follow the failed response.

  1. Write The record is saved.

    The database commits before the response reaches the client.

  2. Timeout The response is lost.

    The client cannot tell whether the write succeeded.

  3. Retry A second record appears.

    A new request key makes the retry look like a new operation.

Why this matters
A timeout is not a rollback.

It describes what the client received, not what the database saved.

One key, one operation.

The request key connects multiple attempts to the same intended write.

03

Keep identity outside the retry.

Create the key once. Each attempt sends that same key so the server can return the stored result.

Retry boundary TypeScript 
// Keep one key for the whole operation.
const key = crypto.randomUUID();
await retry(() =>
  createRecord({ key, payload })
);

The server must atomically associate the key with the saved result. Client code alone does not prevent duplicates.

What changes when the same key arrives again?

The server looks up the saved result for that operation and returns it instead of writing a second record.

Implementation note
The boundary is the operation.

Putting key creation inside the retry callback assigns a new identity to each attempt, defeating duplicate protection.
